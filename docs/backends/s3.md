# AWS S3 Backend

Syncs the bundle to an S3 bucket using the AWS CLI.

Also works against S3-compatible object stores — Cloudflare R2, MinIO,
Backblaze B2 — which serve the same S3 API and are driven through this same
`aws` CLI. They need to be told where to send the request; see
[S3-compatible stores](#s3-compatible-stores-cloudflare-r2) below.

## Prerequisites

```bash
# macOS
brew install awscli

# Linux
pip install awscli
```

## Setup

1. **Configure AWS credentials:**
   ```bash
   aws configure
   ```
   Enter your AWS Access Key ID, Secret Access Key, and default region.

2. **Create an S3 bucket:**
   ```bash
   aws s3 mb s3://your-kirocrew-sync-bucket
   ```

3. **Enable versioning (recommended):**
   ```bash
   aws s3api put-bucket-versioning \
     --bucket your-kirocrew-sync-bucket \
     --versioning-configuration Status=Enabled
   ```

4. **Point the backend at your bucket** in `config.sh`:
   ```bash
   export S3_BUCKET="your-kirocrew-sync-bucket"
   export AWS_PROFILE="default"  # or your profile name
   ```

5. **Select the backend:**
   ```bash
   export SYNC_BACKEND=s3
   ./kirocrew-sync.sh push
   ```

   Or set it permanently in `config.sh`:
   ```bash
   export SYNC_BACKEND="s3"
   ```

## Settings

| Variable | Default | Meaning |
| --- | --- | --- |
| `S3_BUCKET` | `your-bucket-name` | Bucket the bundle is written to |
| `S3_PREFIX` | `kirocrew-sync` | Key prefix (folder) inside the bucket |
| `AWS_PROFILE` | `default` | AWS CLI profile used for credentials |
| `S3_ENDPOINT_URL` | *(empty)* | S3-compatible endpoint; empty means AWS S3 |
| `S3_REGION` | *(empty)* | Region passed to every call; empty leaves it to the profile |

Each is read from the environment first, so you can override any of them in
`config.sh` instead of editing `backends/s3.sh`.

`S3_ENDPOINT_URL` and `S3_REGION` reach every `aws` call this backend makes —
the bucket probe that precedes each push and pull, both `aws s3 sync`s, and
the remote listings behind `backend_list` and `status` — and only when they
are non-empty. Left unset, nothing is appended and the commands are the ones
this backend has always run, argument for argument;
`tests/test_backend_s3_endpoint.sh` asserts those exact command lines.

## S3-compatible stores (Cloudflare R2)

> `./onboard.sh` (repo root) automates this whole section — account
> discovery via wrangler OAuth, the config file, credential storage under
> the right profile, and the reachability probe. The steps below are what
> it does, for when you want them by hand.

R2 is S3-API-compatible: the same `aws` CLI, the same `s3 sync` and `s3 ls`
calls this backend already makes. Only two things differ — the endpoint the
request goes to, and the region name.

1. **Create the bucket** in the Cloudflare dashboard, under R2.

2. **Create an R2 API token** (R2 → *Manage R2 API Tokens*). It yields an
   Access Key ID and a Secret Access Key, and shows the S3 endpoint for your
   account. Those are R2's own credentials, not AWS ones.

3. **Store them in an `aws` CLI profile.** The backend authenticates through
   the profile in `AWS_PROFILE` exactly as it does for AWS, so R2's keys go
   in `~/.aws/credentials` like any other profile:
   ```bash
   aws configure --profile r2
   # AWS Access Key ID     -> the R2 token's Access Key ID
   # AWS Secret Access Key -> the R2 token's Secret Access Key
   # Default region name   -> auto
   ```

4. **Get the endpoint URL.** It is account-level and always of the form
   `https://<account-id>.r2.cloudflarestorage.com`. Your account ID is in the
   R2 overview page, and the bucket's own *Settings* page shows the same host
   with the bucket appended — use the host only, without the bucket.

5. **Configure it** in `config.sh`:
   ```bash
   export SYNC_BACKEND="s3"
   export S3_BUCKET="kirocrew-state"
   export AWS_PROFILE="r2"
   export S3_ENDPOINT_URL="https://<account-id>.r2.cloudflarestorage.com"
   export S3_REGION="auto"
   ```

`S3_REGION=auto` matters: `auto` is the region R2 documents for its S3 API,
and with nothing set the CLI falls back to whatever region the profile carries
— or to none at all. A signature or region mismatch on the first call is the
usual symptom of getting this wrong.

Two caveats worth stating plainly:

- **Versioning and retention are the provider's, not AWS's.** Step 3 of the
  AWS setup above (`aws s3api put-bucket-versioning`) is an AWS call; on an
  S3-compatible store, configure the equivalent in that provider's own
  console instead of assuming the API call exists.
- **This has been exercised against a stub `aws`, not against a live R2
  bucket.** `tests/test_backend_s3_endpoint.sh` asserts the exact command
  lines the backend runs, with and without an endpoint configured. That the
  commands are right is tested; that R2 accepts them is not — see GOAL.md,
  "Never run end-to-end against a real remote backend", which applies to
  every backend here.

The same two settings point the backend at MinIO, Backblaze B2 or any other
store that speaks the S3 API; only R2's values are documented above because
that is the one this repo's author uses.

## Usage

```bash
./kirocrew-sync.sh push     # aws s3 sync bundle -> s3://$S3_BUCKET/$S3_PREFIX/
./kirocrew-sync.sh pull     # aws s3 sync s3://$S3_BUCKET/$S3_PREFIX/ -> bundle
./kirocrew-sync.sh status   # bucket reachability and last remote sync time
```

Push runs with `--delete`, so the remote prefix mirrors the bundle exactly.
`.lock` and `.tmp` files are excluded in both directions.

## Troubleshooting

```bash
# Check AWS credentials
aws sts get-caller-identity

# List bucket contents
aws s3 ls s3://your-bucket/kirocrew-sync/
```

If `push` or `pull` fails with "Cannot access S3 bucket", the profile in
`AWS_PROFILE` either lacks credentials or has no access to `S3_BUCKET` — the
backend probes with `aws s3 ls` before every operation. The message it prints
names the endpoint when one is configured, and suggests commands carrying the
same `--endpoint-url` / `--region` the backend itself uses.

On an S3-compatible store, check in this order:

```bash
# Same probe the backend runs, with the flags it would pass
aws s3 ls "s3://$S3_BUCKET" --profile "$AWS_PROFILE" \
  --endpoint-url "$S3_ENDPOINT_URL" --region "$S3_REGION"
```

- A signature or region error usually means `S3_REGION` is missing or wrong
  (`auto` for R2).
- A DNS or connection error usually means the endpoint host is wrong — it is
  the account host, with no bucket path appended.
- `aws sts get-caller-identity` is an AWS-only call; it will not work against
  a non-AWS endpoint, so use the `aws s3 ls` probe above instead.
- If uploads fail on a checksum or unexpected `x-amz-*` header, check the
  provider's own documentation for the AWS CLI version you have: recent CLI
  releases added request checksums that S3-compatible stores had to catch up
  with.

## Security

- AWS credentials live in `~/.aws/credentials` and are never part of this repo.
  So do an S3-compatible store's keys, in whichever profile `AWS_PROFILE`
  names — `config.sh` holds only the bucket, endpoint and profile name.
- Data in transit is HTTPS.
- The bundle contains your full chat history and knowledge base — keep the
  bucket private, and prefer a dedicated IAM user scoped to this one bucket.
